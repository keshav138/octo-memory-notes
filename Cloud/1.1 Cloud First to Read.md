**1. Docker: Architecture, Isolation & Runtime Mechanics**

  

- **Containers Are Not Lightweight VMs:**
    
      
    - Containers have no hypervisor, no guest kernel, and no virtual hardware. A container is simply a standard Linux process running directly on the host kernel, restricted by **namespaces** (visibility boundary) and **cgroups** (resource boundary).
        
          
        
- **Linux Namespaces vs. cgroups:**
    
      
    - **Namespaces (Isolation - "What I can see"):** `pid` (process tree), `net` (network interfaces/routing), `mnt` (filesystem mounts), `ipc` (shared memory), `uts` (hostname), `user` (UID/GID mapping).
        
          
        
    - **cgroups (Limits - "What I can use"):** CPU shares/quotas, memory limits, blkio (disk I/O throttle), pids (preventing fork-bombs via `pids.max`).
        
          
        
- **The PID 1 Zombie Reaping Problem:**
    
      
    - If an application inside a container runs as PID 1, it must act as the init system. In Linux, standard processes rely on PID 1 to reap orphaned child processes. If your container process doesn't handle `SIGCHLD`, zombies accumulate until `pids.max` is exhausted.
        
          
        
    - PID 1 does not get default signal handlers assigned by the kernel. A raw `SIGTERM` sent by `docker stop` will be ignored unless the process explicitly registers a signal handler, causing Docker to wait 10 seconds and issue a violent `SIGKILL`. Fix: Use lightweight inits like `tini` (`docker run --init`).
        
          
        
- **`ENTRYPOINT` vs. `CMD` Interaction:**
    
      
    - `ENTRYPOINT` defines the executable; `CMD` provides the default arguments.
        
          
        
    - If both use exec form `["executable"]`, `CMD` is appended to `ENTRYPOINT`.
        
          
        
    - _Gotcha:_ If `ENTRYPOINT` uses shell form (`ENTRYPOINT command param`), it executes as `/bin/sh -c`, completely ignoring any CLI parameters or `CMD` directives and refusing to forward signals (breaking clean shutdown).
        
          
        
- **Storage Drivers & OverlayFS:**
    
      
    - Uses a Union Mount filesystem consisting of read-only image layers (`lowerdir`) and a single read-write container layer (`upperdir`).
        
          
        
    - Writes to existing files trigger a **Copy-up** overhead (the entire file is copied from the lower layer to the upper layer before the write executes).
        
          
        
- **Twisted Question:** _"If you set `--memory=512m` on a container running a Java/Node process and the host has 64GB RAM, why does the container get killed with an OOMKilled (Exit Code 137) unexpectedly?"_
    
      
    - **Answer:** Older runtimes/JVMs read `/proc/meminfo` to size heaps, which reports the **host's 64GB**, not the cgroup limit. The runtime sizes its heap for 16GB+, rapidly breaches the 512MB cgroup threshold, and gets terminated by the Linux kernel's **OOM Killer** (not by Docker).
        
          
        

**2. Kubernetes: Control Plane, Scheduling & Networking**

  

- **Control Plane State Machine:**
    
      
    - Only `kube-apiserver` communicates with `etcd`. No other component (`kube-scheduler`, `kube-controller-manager`, `kubelet`) ever talks directly to `etcd`.
        
          
        
    - The API server is stateless and enforces validation, admission webhooks, and optimistic concurrency control via `resourceVersion` (if two writes submit the same version, the slower one receives a 409 Conflict).
        
          
        
- **The Kubernetes Networking Model (The 3 Fundamentals):**
    
      
    1. Every Pod gets its own unique IP address within the cluster.
        
          
        
    2. Containers inside the same Pod share the same network namespace (`netns`), loopback adapter, and IP (they communicate over `localhost`).
        
          
        
    3. Pods can communicate with all other Pods on any node without NAT.
        
          
        
- **ClusterIP & `kube-proxy` Under the Hood:**
    
      
    - A `ClusterIP` does **not** exist on any physical or virtual network interface. It is a virtual routing construct maintained by `kube-proxy` using Linux **iptables** or **IPVS** (or eBPF via Cilium).
        
          
        
    - In iptables mode, incoming traffic to a ClusterIP hits a chain of PREROUTING rules that pick an endpoint pod via probabilistic matching (random load balancing) and perform Destination NAT (DNAT).
        
          
        
- **Pod Termination Grace Period Lifecycle:**
    
      
    
    1. Pod set to `Terminating`; removed immediately from Service endpoints.
        
          
        
    2. Concurrently, `preStop` hook executes, and `SIGTERM` is sent to the container.
        
          
        
    3. `kube-proxy` and ingress controllers asynchronously update iptables/endpoints across nodes.
        
          
        
    
    - _The Race Condition Trap:_ If your app shuts down immediately upon receiving `SIGTERM`, it drops in-flight connections because other nodes haven't finished propagating the removed endpoint from iptables yet. Fix: Introduce a sleep in `preStop` (e.g., `sleep 10`) to allow network routing tables to drain before stopping.
        
          
        
- **Liveness vs. Readiness vs. Startup Probes:**
    
      
    - **Liveness:** Did the app deadlock or hang? Failure triggers a container **restart**.
        
          
        
    - **Readiness:** Can the app serve traffic right now (e.g., database connection pool full)? Failure **removes the Pod from Service endpoints** without restarting it.
        
          
        
    - _Interview Trap:_ Making a liveness probe check external dependencies (e.g., an external database). If the DB slows down, all pods fail liveness and restart simultaneously, turning a DB bottleneck into a complete cascading cluster crash.
        
          
        
- **Twisted Question:** _"What is the difference between a Pod's `requests` and `limits` in terms of CPU and Memory scheduling?"_
    
      
    - **Answer:**
        
          
        - `requests` is used strictly by `kube-scheduler` to find a node with sufficient allocatable capacity.
            
              
            
        - At the kernel level, **CPU request** sets `cpu.shares` (relative weight when contended). **CPU limit** sets `cpu.cfs_quota_us` (hard throttling; CPU never gets OOM killed, it just throttles).
            
              
            
        - **Memory limit** sets `memory.max`. If exceeded, the kernel immediately terminates the container with `OOMKilled` (Exit Code 137).
            
              
            

**3. Jenkins: Pipelines, Architecture & Security**

  

- **Controller-Agent Topology & Master Architecture:**
    
      
    - The Controller executes the orchestration engine, parses pipeline state, serves the UI, and coordinates logs. It should **never** execute build jobs directly (executor count on controller must be 0) to avoid arbitrary build scripts hijacking the controller filesystem or SSH keys.
        
          
        
    - Agents run the build workspace and connect via JNLP/Inbound agents (TCP/WebSocket) or outbound SSH.
        
          
        
- **Scripted vs. Declarative Pipelines:**
    
      
    - **Declarative:** Strict, predefined syntax (`pipeline { agent any; stages { ... } }`). Enforces structured validation, built-in post actions, and syntax linting before execution starts.
        
          
        
    - **Scripted:** Groovy-based domain-specific language (`node { ... }`). Unrestricted procedural flow; executes directly inside the Groovy CPS interpreter.
        
          
        
- **The Continuation-Passing Style (CPS) Interpreter & Serialization:**
    
      
    - Jenkins can survive a controller reboot mid-pipeline without losing execution state because it runs code through an asynchronous CPS transformation that serializes every execution step to disk.
        
          
        
    - _Classic Trap (`NotSerializableException`):_ Writing complex Groovy objects, non-serializable classes, or closures that retain references to non-serializable objects inside a pipeline script will crash the build when Jenkins attempts to persist the pipeline state. Fix: Mark methods with `@NonCPS`.
        
          
        
- **Shared Libraries:**
    
      
    - Stored in a separate Git repository; provides reusable pipeline steps across an enterprise.
        
          
        
    - Evaluated in an untrusted or trusted Groovy sandbox. Changes to `vars/customStep.groovy` are dynamically loaded at runtime based on the library branch mapped.
        
          
        
- **Docker-in-Docker (DinD) vs. Mounting the Host Socket (DooD):**
    
      
    - **DinD (`docker:dind`):** Runs an actual Docker daemon inside a container. Requires `--privileged` mode (dangerous, circumvents host cgroups/security).
        
          
        
    - **DooD (Docker-outside-of-Docker):** Mounts the host `/var/run/docker.sock` into the Jenkins agent container. Avoids privileged mode, but effectively grants the container **root access to the host machine**, because anyone who can talk to the Docker socket can spin up a container with the host root filesystem mounted at `/`.
        
          
        
- **Twisted Question:** _"Why should you never use `git pull` or rely on local workspace state inside Jenkins build steps?"_
    
      
    - **Answer:** Agents are ephemeral; subsequent stages or parallel steps can execute on entirely different worker nodes with disconnected local filesystems. Pipelines must treat the workspace as disposable, relying on atomic SCM checkouts and stash/unstash primitives.
        
          
        

**4. Terraform: State Management, Dependency Graphs & Engine Internals**

  

- **The Dependency Graph & DAG Execution:**
    
      
    - Terraform builds a Directed Acyclic Graph (DAG) of all resources defined in configuration.
        
          
        
    - Independent resources are created in parallel (default `--parallelism=10`).
        
          
        
    - Implicit dependencies (referencing `aws_security_group.sg.id` inside `aws_instance.web`) automatically order DAG nodes. `depends_on` should only be used for hidden dependencies that Terraform cannot detect via attributes (e.g., waiting for an IAM role propagation).
        
          
        
- **Terraform State (`terraform.tfstate`) Internal Purpose:**
    
      
    - Maps declared configuration code to real-world cloud API IDs.
        
          
        
    - Tracks metadata like resource dependencies and sensitive outputs.
        
          
        
    - Improves performance by acting as a cache for immutable attributes so Terraform doesn't have to query every cloud API endpoint during every operation.
        
          
        
- **Remote State Locking:**
    
      
    - Prevents concurrent `apply` or `plan` executions by multiple engineers, which would corrupt the state file.
        
          
        
    - Example: Uses AWS S3 for state storage with DynamoDB (or S3-native conditional writes) for atomic locking via a `LockID`.
        
          
        
- **Terraform Refresh vs. Plan vs. Apply:**
    
      
    - **`refresh`:** Queries the cloud APIs to update the state file with the current real-world state (detects **drift**).
        
          
        
    - **`plan`:** Computes the delta: $\text{Desired Config} - \text{State post-refresh}$. Produces an execution plan with strict actions: `+` (create), `~` (in-place update), `-` (destroy), `-+/+-` (recreate).
        
          
        
    - **`apply`:** Executes only the graph operations determined by the plan and commits the new state.
        
          
        
- **Tainted Resources vs. Replace:**
    
      
    - In older Terraform versions, `terraform taint` manually marks a resource as degraded so the next plan destroys and recreates it.
        
          
        
    - Modern Terraform (v0.15.2+) deprecates this in favor of `terraform apply -replace="aws_instance.web"`.
        
          
        
- **Twisted Question:** _"If someone manually deletes an EC2 instance in the AWS Console, what does `terraform plan` output, and what does it do to the state file?"_
    
      
    - **Answer:** During the plan phase, the refresh cycle queries AWS API, receives a `404 Not Found`, and recognizes the drift. The generated plan will state that the instance needs to be **created (`+`)**. Critically, the state file on disk is **not** modified during `terraform plan`; the state is only updated when `terraform apply` is run to reconcile the delta.
        
          
        

**5. Quick Edge-Case Verification Table**

|**Component**|**The Common Assumption**|**The Twisted Reality / Edge Case**|
|---|---|---|
|**Docker Base**|`alpine` is always the best lightweight base.|Uses `musl` libc instead of `glibc`. Can cause silent thread stack bugs, memory allocation latency with C-extensions, or performance regressions in Python/Go/Node.|
|**K8s CPU Limit**|Setting CPU limit guarantees dedicated CPU.|CPU limits use Completely Fair Scheduler (CFS) quotas. Exceeding your quota within a 100ms enforcement window results in aggressive thread freezing/throttling, even if total CPU usage across the node is low.|
|**K8s Scheduling**|Pods land on nodes with the most free RAM.|Scheduler prioritizes nodes based on unallocated **requested** memory, not actual real-time physical RAM usage on the host.|
|**Jenkins Master**|High build load slows down the UI web server.|True if executors run on master, but often caused by massive build history retaining thousands of pipeline runs in disk-backed XML files (`builds/` directory).|
|**Terraform Target**|`terraform apply -target=...` is a safe hotfix tool.|Bypasses the dependency DAG for untargeted resources, easily stranding state references, causing state drift, and producing broken dependencies on the next global run.|
