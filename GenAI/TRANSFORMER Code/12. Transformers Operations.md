Let me lay out the full picture — these terms cluster into two "modes" the same model operates in, plus a handful of techniques that only make sense once you see which mode they belong to.

## The two fundamental modes

**Training mode** — the model already knows the correct answer (the `label`) and is being taught to predict it. Loss is computed, gradients flow backward, weights update. This is what your `train_model` loop does.

**Inference mode** — the model does _not_ know the answer. It has to generate one, token by token, using only what it's produced so far. No loss, no backward pass, no gradient. This is what `greedy_decode` does.

Everything else below is really just: "which of these two situations does this term apply to?"

## Teacher forcing (training-mode technique)

At training time, instead of making the model use its _own_ (possibly wrong) previous prediction as input for the next step, you feed it the **real** previous token from the ground-truth sentence — you "force" the correct answer at every position, like a teacher standing over your shoulder correcting each word before you write the next one.

Concretely, for target `"je vais bien"`: the decoder is shown `[SOS] je vais` as input and asked to predict `je vais bien [EOS]` — all four positions predicted in parallel, in one forward pass, because at each position the ground-truth prefix is already known and handed in.

**Why do this instead of the "honest" way?** Two reasons: (1) speed — one forward pass computes the loss for the whole sentence, instead of running the decoder once per token; (2) stability — early in training, the model's own predictions are near-random garbage, so if you fed those back in, errors would compound and the model would rarely see a sensible sentence to learn from.

**The catch — exposure bias:** the model trains on perfect prefixes, but at inference time it only has its own (imperfect) prefix to work with. A mistake early in generation can snowball, since the model never practiced recovering from its own mistakes during training. This gap between train-time and inference-time conditions is called _exposure bias_. (A partial fix some setups use is **scheduled sampling** — occasionally feed the model's own prediction instead of the ground truth during training, so it gets some practice with imperfect input. Your current loop doesn't do this — most modern transformer setups skip it.)

## Autoregressive generation (inference-mode necessity)

Because inference has no ground truth to force-feed, generation happens one step at a time: predict token 1 → append it → predict token 2 given tokens 1 → append it → predict token 3, and so on, until `[EOS]` or a length limit. "Autoregressive" just means "each output depends on previously generated outputs." This is inherently sequential — you cannot parallelize across positions the way training does, which is why generation is slow compared to training's one-shot forward pass.

## Decoding strategies (how you pick each next token during inference)

Given the model's probability distribution over the vocabulary at each step, how do you choose the actual token?

- **Greedy decoding** — always take the single highest-probability token. Simple, deterministic, what your `greedy_decode` does. Downside: locally optimal choices can lead to a globally worse sentence (a slightly-lower-probability word now might have led to a much better sentence overall).
- **Beam search** — keep the top-_k_ partial sequences at every step instead of just 1, expand each, prune back down to the top-_k_ again. More expensive, usually higher quality. Standard for translation.
- **Sampling** — instead of always taking the max, sample randomly from the probability distribution. Introduces variety; used heavily in open-ended generation (chatbots, creative writing) rather than translation, where you usually want _the_ correct answer, not variety.
    - **Temperature** — a scalar that reshapes the distribution before sampling: low temperature (→0) sharpens it toward greedy behavior, high temperature flattens it toward uniform randomness.
    - **Top-k sampling** — only sample from the k highest-probability tokens, discard the long tail.
    - **Top-p (nucleus) sampling** — sample from the smallest set of tokens whose cumulative probability exceeds p, adapting the pool size dynamically instead of a fixed k.

## Masking — different jobs in each mode, same mechanism

- **Padding mask** — used in _both_ modes, on _both_ encoder and decoder. Just says "ignore `[PAD]` positions, they're not real content."
- **Causal mask** — used in the decoder in _both_ modes, for different reasons. In training, it's needed because teacher forcing hands the model the _entire_ target sequence at once — without the mask, position `i` could see position `i+1`'s answer sitting right there and trivially "cheat." In inference, there's no future to peek at anyway (you haven't generated it yet), so the causal mask is technically redundant there — but it's applied for consistency and because during inference you're still re-running the decoder over a growing `decoder_input` that includes all tokens so far.

## Efficiency terms you'll hit once you look at real inference code

- **KV caching** — the expensive part of autoregressive inference is that a naive implementation recomputes attention over the _entire_ growing sequence at every single new token. KV caching stores the key/value projections from previous steps so each new token only computes attention for itself, not the whole sequence again. Your `greedy_decode` above doesn't do this (it's simple/educational), which is fine for learning but very slow for real serving.
- **Perplexity** — a standard metric for how well the model predicts held-out text; roughly, `exp(average cross-entropy loss)`. Lower is better. Common way to report validation performance for language models.

## One distinction worth pinning down since it trips people up

- **Pretraining vs fine-tuning** is a different axis entirely from training-vs-inference — both are "training mode" (loss + backprop), the difference is just _what data_ and _for what goal_. Pretraining is learning general language patterns from huge unlabeled corpora (this is exactly what your Nepali nanoGPT project is doing — predicting the next token over your Nepali corpus, no translation labels involved). Fine-tuning is continuing to train an already-pretrained model on a smaller, task-specific labeled dataset (like this English→French dataset with actual translation pairs).
