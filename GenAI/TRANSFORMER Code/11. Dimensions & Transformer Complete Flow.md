## Dimensions
> Difference between batch size, seq_size in positional embedding and the other one, and vocab size.

Your understanding is close, with one distinction worth sharpening: `seq_len` isn't really "sentence words" fixed once — there are two different `seq_len`s in play. The one passed to `PositionalEmbedding.__init__` is a **construction-time upper bound** (e.g. 512) — the largest sentence the model will ever be built to support. The one that actually matters at runtime is `x.shape[1]` — however long _this specific batch's_ padded sentences are, always ≤ that upper bound. `vocab_size` is correct as "total distinct tokens the tokenizer knows" — just note it's usually subword units, not whole words.

Now, the real source of confusion: **this code has two completely separate flows that never touch each other in the source order** — a construction-time flow (`build_transformer`, runs once) and a forward-time flow (`encode`/`decode`/`project`, runs every batch). Reading top-to-bottom mixes them because Python defines classes before it ever instantiates or calls them.

**How each construction step maps to code:**
- `build_transformer` runs the `for _ in range(N)` loop **twice** — once creating N fresh `EncoderBlock` instances (each with its own new `MultiHeadAttention` and `FeedForwardBlock`), once for N fresh `DecoderBlock` instances. "Fresh" is the key word: every iteration calls `MultiHeadAttention(d_model, h, dropout)` again, so block 1 and block 2 have completely independent weight matrices, even though they're the same class.
- Those N objects go into a Python list, wrapped in `nn.ModuleList(...)` (so PyTorch tracks all their parameters), and that list is handed to `Encoder(...)` / `Decoder(...)`. **`Encoder` and `Decoder` don't build anything themselves** — they just store the list you hand them (`self.layers = layers`) plus create one `LayerNormalization()` for the end.
- `Transformer(...)` is the outermost wrapper — it just holds references to everything: the two embed layers, two pos layers, the encoder, the decoder, the projection layer. It has no `forward()` method at all — only `encode`, `decode`, `project` as separate callable methods.
- Last step: loop over `transformer.parameters()` (this recursively finds every weight inside every nested submodule) and Xavier-init anything with more than 1 dimension.

**Forward-time flow** — this is _tensors moving_, happens every batch, and only touches `encode`/`decode`/`project`:

- `transformer.encode(src, src_mask)` → `src_embed(src)` → `src_pos(...)` → `encoder(x, mask)`, which internally does `for layer in self.layers: x = layer(x, mask)` — this is where it actually calls each `EncoderBlock.forward` in sequence, block 1's output becomes block 2's input, and so on N times — then one final `self.norm(x)`.
- `transformer.decode(encoder_output, src_mask, tgt, tgt_mask)` → same embed+pos pattern for `tgt` → `decoder(x, encoder_output, src_mask, tgt_mask)`, looping through N `DecoderBlock`s the same way — but note `encoder_output` (the _same_ tensor, computed once) gets passed into **every** decoder block's cross-attention, not consumed or transformed by the loop.
- `transformer.project(decoder_output)` → the final linear + log_softmax.

Nothing in `Transformer` calls `encode`/`decode`/`project` for you — a training loop (not in this file) is expected to call `model.encode(...)` once, then `model.decode(...)`, then `model.project(...)` explicitly.

> So with the four variables in build transformer, for both src and tgt, break them down briefly

The four are `src_vocab_size`, `tgt_vocab_size`, `src_seq_len`, `tgt_seq_len` — each pair exists separately because src and tgt are different languages (or at least different tokenizers), so nothing about one can be assumed from the other.

- **`src_vocab_size`** — size of the source-language vocabulary. Used to build `src_embed = InputEmbeddings(d_model, src_vocab_size)`, i.e. how many rows the source embedding lookup table has.
- **`tgt_vocab_size`** — size of the target-language vocabulary. Used for `tgt_embed`'s embedding table, and also for `ProjectionLayer(d_model, tgt_vocab_size)` — the final output layer's width, since the model only ever predicts _target_-language tokens.
- **`src_seq_len`** — max sentence length the source side will support. Used to build `src_pos = PositionalEmbedding(d_model, src_seq_len, dropout)` — determines how many rows the source positional-encoding table (`pe`) has.
- **`tgt_seq_len`** — max sentence length the target side will support. Same role, but for `tgt_pos`.

In your case (Nepali NLP work), if this were src=English, tgt=Nepali: `src_vocab_size`/`src_seq_len` come from your English tokenizer and its typical sentence lengths, `tgt_vocab_size`/`tgt_seq_len` come from your Nepali tokenizer and its sentence lengths — likely different numbers on both counts, since Nepali's Devanagari subword tokenization won't split the same way English BPE does, and the two languages won't average the same token count per sentence.
