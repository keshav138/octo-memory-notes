```python
class PositionalEmbedding(nn.Module):
    def __init__(self, d_model: int, seq_len: int, dropout: float):
        '''
        d_model: additional matrix that has the same dense vector dimensions
        seq_len: the sentence size
        dropout: kills neurons termporarily to avoid overfitting
        pe: matrix of size (seq_len x d_model)
        '''
        
        super().__init__()
        self.d_model = d_model
        self.seq_len = seq_len
        self.dropout = nn.Dropout(dropout)
    
        pe = torch.zeros(seq_len, d_model)

        # create a vector of size(seq_len) to indicate position of word in sentence. Range(0, n-1)
        position = torch.arange(0, seq_len, dtype=torch.float).unsqueeze(1) # (seq_len, 1)

        div_term = torch.exp(torch.arange(0, d_model, 2).float() * (-math.log(10000.0) / d_model))

        pe[:, 0::2] = torch.sin(position * div_term)
        pe[:, 1::2] = torch.cos(position * div_term)
        
        pe = pe.unsqueeze(0) # (1, seq_len, d_model) , batch dimension, as in for multiple sentences

        self.register_buffer('pe', pe) # to save tensor values when mode is being saved

    
    def forward(self, x):
        x = x + (self.pe[:, :x.shape[1], :]).requires_grad_(False) # to void this from being learned in backprop
        return self.dropout(x)



```

This is one of the most important pieces of the original Transformer. I'll explain **what every line is doing**, but more importantly, **why** it exists.

First, let's remember where this fits in the pipeline.

```text
Sentence
    │
Tokenizer
    │
Token IDs
    │
Embedding Layer
    │
(batch_size, seq_len, d_model)
    │
+ Positional Encoding  ← This class
```

The embedding layer knows **what** each word is, but it has no idea **where** it appears in the sentence.

For example,

```text

and

```

contain exactly the same words.

Without positional information, the embeddings would just be

```text

```

or

```text

```

and the transformer wouldn't know which came first.

# Why sine and cosine?

Because they have useful mathematical properties.

Nearby positions produce similar vectors.

```
Position 5

↓

vector A

Position 6

↓

vector B

A and B are similar.
```

But

```
Position 5

Position 95
```

produce very different vectors.

This helps attention learn distances.

## Why `.requires_grad_(False)`?

Your code uses:

```python
.requires_grad(False)
```

The usual PyTorch style is:

```python
.requires_grad_(False)
```

or simply relying on the fact that `register_buffer` already creates a non-trainable tensor.

The intent is the same: **do not compute gradients for the positional encoding**, because in the original Transformer these values are fixed mathematical functions, not learned parameters.

# Doubt

> still dont understand the need for the slicing, isnt the sentence that passes through the input embedding also pass throght he pe, therefore both having the same seq_length
You're right that `x`'s seq_len and the sliced `pe`'s seq_len end up matching — that's exactly the point of the slicing. Let me clarify what's actually variable here.

`self.pe` is built **once**, in `__init__`, at whatever `seq_len` you passed when constructing the model — call it the _max_ supported length (e.g. 512). It's a buffer, fixed for the model's whole lifetime: `pe.shape = (1, 512, d_model)`.

But `x` arriving in `forward` isn't always 512 tokens long. Different batches have different sentence lengths — a batch of short Nepali sentences might be `(batch, 40, d_model)`, another batch might be `(batch, 120, d_model)`. `x.shape[1]` is whatever that particular batch's length is, and it's very often _less than_ the 512 the `pe` table was built for.

So `self.pe[:, :x.shape[1], :]` isn't matching two independently-varying things — it's cropping the one big fixed table down to only the first `x.shape[1]` rows, so it lines up with however long _this specific batch_ happens to be. Without the slice, you'd try to add a `(1, 512, d_model)` tensor to a `(batch, 40, d_model)` tensor and get a shape mismatch error.

Concretely: `pe[0]` = position 0's vector, `pe[1]` = position 1's vector, ... `pe[511]` = position 511's vector, precomputed once. If your batch has 40-token sentences, you only need `pe[0]` through `pe[39]` — the slice grabs exactly that.
