Here's the walkthrough, concept by concept, with why each step exists.

## 1. Why you can't just `json.load()` the file

22GB won't fit in Colab's RAM (~12-16GB free tier). You need to read it **incrementally** instead of parsing the whole file into a Python object at once.

Two cases depending on actual file structure:

- **If it's one giant JSON array** `[{...}, {...}, ...]` (looks like it, from your screenshot) → use the `ijson` library, which parses JSON incrementally, yielding one object at a time without loading the rest.
- **If it were JSONL** (one JSON object per line, no wrapping array) → you'd just do `for line in file: json.loads(line)`. Worth checking with `head -c 500 file.json` first — if it starts with `[` and objects are comma-separated, it's the array case.

```python
import ijson

with open('corpus.json', 'rb') as f:
    for obj in ijson.items(f, 'item'):  # 'item' = each element of the top-level array
        # obj is one document dict, process and discard — never accumulates in memory
        process(obj)
```

## 2. Extracting the actual text

From your screenshot, each doc has `page_1`, `page_2`, `page_3`... keys (variable count per doc), each with a nested `text_data` string. You need to:

```python
for key, val in obj.items():
    if key.startswith('page_') and isinstance(val, dict):
        text = val.get('text_data', '')
```

Concatenate all pages per document (in page order — sort keys numerically, not lexically, since `page_10` < `page_2` alphabetically) into one running text, or keep them as separate chunks — separate chunks is actually better for you, more on why below.

## 3. Unicode normalization (new concept, important)

Devanagari (the script Nepali uses) has a quirk: the _same visual character_ can be represented by different underlying byte sequences — e.g., a consonant+vowel-sign combo can sometimes be encoded as one precomposed character or as two separate codepoints that render identically. If you don't normalize, your tokenizer will treat visually-identical text as different tokens, wasting vocab and hurting learning.

Fix: run every string through NFC normalization.

```python
import unicodedata
text = unicodedata.normalize('NFC', text)
```

Do this once, early, on every extracted string.

## 4. OCR noise cleaning

Your sample text has garbage like `"$5911001 19०."` and `"२०७६"` mixed with corrupted fragments — this is PDF/OCR extraction noise, not real Nepali text. Since your source docs were OCR'd or converted from PDFs, you'll have:

- Random Latin characters/digits injected mid-Devanagari text
- Broken words split by extraction artifacts
- Page headers/footers/page numbers repeated (e.g., "ठाउँ?", numeric codes) leaking into `text_data`

Practical filtering (regex-based, not fancy):

```python
import re

devanagari_range = r'\u0900-\u097F'

def devanagari_ratio(text):
    if not text: return 0
    dev_chars = len(re.findall(f'[{devanagari_range}]', text))
    return dev_chars / len(text)

# Keep only chunks where most content is actually Nepali script
if devanagari_ratio(text) < 0.6:
    discard(text)
```

This single ratio check kills a lot of garbage cheaply — pages that are mostly stray Latin/numeric OCR junk get dropped.

You can also strip obvious junk patterns (long digit runs, repeated headers) with a few `re.sub()` rules, but don't over-engineer this — diminishing returns for a 2-week project. A ratio filter + NFC normalization gets you 80% of the value.

## 5. Deduplication

Books/documents in a scraped corpus often repeat (same book uploaded twice, boilerplate front-matter, repeated table-of-contents pages). Exact duplicates are cheap to catch:

```python
seen_hashes = set()
h = hash(text.strip())
if h in seen_hashes:
    discard()
seen_hashes.add(h)
```

Near-duplicates (minor OCR variation of the same page) are a bigger topic (MinHash/LSH) — skip it, not worth the time for your timeline.

## 6. Chunk size decision

Language models train on fixed-length sequences (e.g., 512 or 1024 tokens). Rather than concatenating everything into one giant blob, keep text chunked at roughly page/paragraph granularity, then when you build training data you concatenate-and-slice into fixed-length blocks anyway (standard nanoGPT approach: tokenize everything, concatenate into one long token stream, slice into blocks). So really, the pipeline's job is just: **produce one big clean `.txt` file** (or a few `.txt` shards), one cleaned+normalized text chunk per line, ready to hand to the tokenizer stage.

## 7. Output + split

```python
# Write to shards to avoid one giant unwieldy file
with open('train.txt', 'w', encoding='utf-8') as train_f, \
     open('val.txt', 'w', encoding='utf-8') as val_f:
    for i, text in enumerate(cleaned_texts):
        f = val_f if i % 20 == 0 else train_f  # ~5% val
        f.write(text.strip() + '\n')
```

## Summary of the pipeline in order

1. Stream-parse JSON with `ijson` (don't load whole file)
2. Extract `text_data` from all `page_N` keys per doc, sorted correctly
3. NFC-normalize every string
4. Filter by Devanagari-character ratio (drop junk pages)
5. Dedupe exact repeats via hashing
6. Write out clean train.txt / val.txt, target ~1-2GB total after filtering
7. Hand off to tokenizer training (SentencePiece on train.txt)

That last handoff is where the "data pipeline" team's job ends and the tokenizer/model team's begins.
