Unicode normalization is one of those things that seems unnecessary until you work with multilingual text. Once you're training an LLM—especially on Hindi, Tamil, Arabic, Korean, or accented Latin languages—it becomes extremely important.

---

# The Problem Unicode Tries to Solve

Computers don't actually store characters.

They store **code points**.

For example:

```
A
```

is stored as

```
U+0041
```

Similarly,

```
अ
```

is

```
U+0905
```

Every character has a unique number.

---

## The Problem

Sometimes **the exact same visible character can be represented in multiple ways.**

Consider the letter:

```
é
```

There are two possible Unicode representations.

### Method 1 (single code point)

```
é

↓

U+00E9
```

One character.

---

### Method 2 (two code points)

```
e

↓

U+0065

+

◌́

↓

U+0301
```

The accent is stored separately.

Visually:

```
e + ◌́

↓

é
```

Looks identical.

Internally:

```
[101, 769]
```

instead of

```
[233]
```

---

To Python:

```python
a = "é"
b = "e\u0301"

print(a == b)
```

Output:

```
False
```

Even though they look identical.

---

# Why This Breaks NLP

Suppose your corpus contains

```
Café
```

stored one way.

Another document contains

```
Café
```

stored the other way.

Tokenizer sees

```
Café

≠

Café
```

So your vocabulary becomes

```
"Café"

"Café"
```

Two different tokens.

The model thinks they are different words.

Training quality decreases.

---

# Unicode Normalization

Normalization converts different Unicode representations into a **single standard representation**.

Think of it as:

```
Different spellings

↓

Canonical form

↓

Tokenizer
```

---

Python provides this through

```python
import unicodedata
```

---

# NFC

The most commonly used normalization.

```python
unicodedata.normalize("NFC", text)
```

NFC means

```
Normalization Form C

C = Composed
```

It combines characters whenever possible.

Example:

Before:

```
e

+

◌́
```

After NFC:

```
é
```

Single code point.

---

Example

```python
import unicodedata

s = "e\u0301"

print(len(s))
```

Output

```
2
```

Normalize

```python
s = unicodedata.normalize("NFC", s)
```

Now

```
len(s)
```

becomes

```
1
```

---

Visual

Before

```
e
↓

Accent

↓

Stored separately
```

After

```
é
```

---

# NFD

Opposite of NFC.

```
Normalization Form D

D = Decomposed
```

Instead of

```
é
```

it becomes

```
e

+

◌́
```

Always split.

Example

```python
unicodedata.normalize("NFD", "é")
```

returns

```
e + accent
```

---

Visual

```
é

↓

e

↓

accent
```

---

# NFKC

Now things become more interesting.

NFKC

```
Normalization Form

Compatibility

Composed
```

Not only combines accents,

it also converts **compatibility characters**.

Example

```
①
```

becomes

```
1
```

Another example

```
Ⅳ
```

Roman numeral

↓

```
IV
```

Another

```
ＦＵＬＬＷＩＤＴＨ
```

↓

```
FULLWIDTH
```

---

NFKC changes the actual representation.

Useful for search.

Sometimes undesirable for preserving exact text.

---

# NFKD

Compatibility decomposition.

Everything gets expanded.

---

# Four Forms

|Form|What it does|
|---|---|
|NFC|Compose characters|
|NFD|Decompose characters|
|NFKC|Compatibility + Compose|
|NFKD|Compatibility + Decompose|

---

# Which One for LLM Training?

Almost always

```
NFC
```

Why?

Because you want

- Preserve meaning
    
- Preserve script
    
- Remove duplicate encodings
    

without changing text.

---

# Hindi Example

Hindi has combining marks called **matras**.

Example

```
कि
```

is actually

```
क

+

ि
```

Notice

The vowel appears visually **before** the consonant

```
कि
```

But internally

```
क

↓

ि
```

Unicode stores it logically, not visually.

---

Suppose two sources produce

```
कि
```

using slightly different combining sequences.

Without normalization

```
कि

≠

कि
```

possible internally.

Tokenizer may split them differently.

NFC fixes this.

---

# Why Hugging Face Uses NFC

Most tokenizer training pipelines do

```
Raw text

↓

Unicode normalization

↓

Whitespace cleanup

↓

Tokenizer training
```

Because vocabulary becomes cleaner.

Instead of

```
é

Café

Café

Café
```

all become

```
Café
```

---

# Typical Preprocessing Pipeline

```
Read JSON

↓

Extract text

↓

Unicode NFC

↓

Remove invalid characters

↓

Whitespace normalization

↓

Tokenizer

↓

```

# Python Example

```python
import unicodedata

text = "Cafe\u0301"

normalized = unicodedata.normalize("NFC", text)

print(text)
print(normalized)
```

Looks identical.

Internally different.

---

# Checking Equality

```python
a = "é"

b = "e\u0301"

print(a == b)
```

False.

Normalize

```python
a = unicodedata.normalize("NFC", a)
b = unicodedata.normalize("NFC", b)

print(a == b)
```

Now

```
True
```

---

# How Much Memory Does It Use?

Very little.

It processes one string.

For your `ijson` pipeline:

```python
import unicodedata
import ijson

with open("large.json", "rb") as f:
    for item in ijson.items(f, "item"):
        text = item.get("text", "")
        text = unicodedata.normalize("NFC", text)

        # Tokenize or save
```

You normalize each document as it's streamed, so memory usage stays essentially constant.

---

# Does NFC Change Hindi Text?

Usually **no visible change**.

For most well-formed Hindi text:

```
राम घर गया।
```

↓

NFC

↓

```
राम घर गया।
```

Exactly the same.

What changes is the **internal encoding**, making equivalent character sequences consistent.

---

# When Should You Use NFC?

For an LLM preprocessing pipeline, NFC should happen **before tokenization** and **before training the tokenizer**.

```
Raw scraped text
        │
        ▼
Unicode NFC normalization
        │
        ▼
Whitespace cleanup
        │
        ▼
(Optional) Remove control characters
        │
        ▼
Train tokenizer
        │
        ▼
Convert to token IDs
        │
        ▼
Train decoder model
```

This ensures that equivalent Unicode sequences map to the same tokens, reducing vocabulary fragmentation and making training more efficient.
