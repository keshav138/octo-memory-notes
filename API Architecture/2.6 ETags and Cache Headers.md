An **ETag** (Entity Tag) is an HTTP response header that acts as a unique fingerprint or version identifier for a specific representation of a resource (typically an MD5 hash of the content or a revision number).

  

Together with standard caching headers, ETags enable **conditional requests**—allowing browsers and CDNs to check whether cached content is still fresh without re-downloading the entire response body.

  

**The Two Stages of HTTP Caching**

  

HTTP caching generally relies on two phases:

  

1. **Freshness validation (`Cache-Control: max-age`):** The client uses the cached copy directly from its disk or memory without contacting the server at all as long as the time hasn't expired.
    
      
    
2. **Revalidation (`ETag` + `If-None-Match`):** Once the cached copy becomes "stale" (or if `no-cache` is used), the client asks the origin server: _"Has this resource changed since this specific ETag was issued?"_
    
      
    

**Step-by-Step Lifecycle**

  

1. **Initial Request (Fresh Fetch):**
    
      
    - The client requests a resource: `GET /api/user/101`.
        
          
        
    - The server responds with the payload and assigns an ETag:
        
          
        
        HTTP
        
        ```
        HTTP/1.1 200 OK
        Cache-Control: public, max-age=3600, no-cache
        ETag: "68b329da9893e34099c7d8ad5cb9c940"
        Content-Length: 1048576
        
        { ...1MB of payload... }
        ```
        
    - The client caches both the body and the associated `ETag`.
        
          
        
2. **Subsequent Request (Conditional Validation):**
    
      
    - The client needs the resource again. Instead of requesting a full download, it sends a conditional GET using the **`If-None-Match`** header containing the stored ETag:
        
          
        
        HTTP
        
        ```
        GET /api/user/101
        If-None-Match: "68b329da9893e34099c7d8ad5cb9c940"
        ```
        
3. **Server Evaluation:**
    
      
    - **Case A: Resource Has Not Changed:** The server computes the current resource hash, sees that it matches `"68b329da..."`, and replies with an empty body:
        
          
        
        HTTP
        
        ```
        HTTP/1.1 304 Not Modified
        ETag: "68b329da9893e34099c7d8ad5cb9c940"
        ```
        
        _Result:_ Zero body bytes sent over the network; the client safely reuses its cached copy.
        
          
        
    - **Case B: Resource Changed:** The server's hash differs from the client's token. It sends a standard `200 OK` with the new data and a new `ETag`.
        
          
        

**Strong vs. Weak ETags**

  

|**Type**|**Syntax**|**Behavior**|**Primary Use Case**|
|---|---|---|---|
|**Strong ETag**|`"xyz123"`|Requires byte-for-byte exact matching of the response body.|Critical files, binary assets, byte-range requests (`Range`).|
|**Weak ETag**|`W/"xyz123"`|Content is semantically identical even if non-critical bytes differ (e.g., compressed vs uncompressed, whitespace changes).|Dynamic HTML/JSON where exact byte alignment across compression layers doesn't matter.|

**ETag vs. `Last-Modified`**

  

While older HTTP caching relies on the `Last-Modified` and `If-Modified-Since` headers, ETags are generally preferred because:

  

- **Sub-second precision:** `Last-Modified` only resolves to the nearest second; rapid updates within one second get missed.
    
      
    
- **Content vs. Metadata:** Touching or re-saving a file without modifying its contents updates the filesystem timestamp (triggering a false invalidation), whereas an ETag based on a content hash remains unchanged.
