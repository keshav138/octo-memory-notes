**1. Process vs. Thread Memory & Context Switching**

  

- **Memory Boundary:** Threads in the same process share the Virtual Address Space (code, data, heap, file descriptors, signals). Each thread has an independent Stack, Program Counter (PC), and CPU registers.
    
      
    

 
- **Heap vs. Stack Race Conditions:** Multi-threading race conditions occur almost exclusively on the **heap** (shared objects/pointers) or static globals. Stacks are thread-local, but passing a stack pointer to another thread exposes it to data races and dangling pointer bugs.
    
      
    
- **Context Switch Overhead:**
    
      
    - Process switch requires updating the CPU CR3 register (base address of page directory), which invalidates the Translation Lookaside Buffer (TLB). Subsequent memory accesses trigger costly page table walks.
        
          
        
    - Thread switch only swaps registers, stack pointer, and program counter. The virtual address space remains identical, keeping the TLB hot.
        
          
        
- **Twisted Question:** _"Can a thread execute code located on another thread's stack?"_
    
      
    - **Answer:** Yes, at the hardware/OS level there is no memory isolation between threads of the same process. If a thread gets a raw memory pointer to another thread's stack frame, it can read/write to it (and corrupt it).
        
          
        

**2. Virtual Memory & Paging Mechanics**

  

- **Virtual to Physical Address Translation:**
    
      
    - Virtual Address split: `[ Virtual Page Number (VPN) | Page Offset ]`.
        
          
        
    - The MMU indexes the Page Table using the VPN to retrieve the Physical Frame Number (PFN) and permission bits (Read/Write/Execute/User).
        
          
        
    - Physical Address = `(PFN * Page_Size) + Page Offset`.
        
          
        
- **Page Fault Sequence:**
    
      
    1. CPU references virtual address whose Page Table Entry (PTE) has `Present Bit = 0`.
        
          
        
    2. MMU raises a hardware page fault exception (interrupt 14 on x86).
        
          
        
    3. CPU context-switches to Kernel Mode, saving registers and faulting address (in `CR2` register).
        
          
        
    4. Kernel inspects virtual memory area (VMA):
        
          
        - Invalid address $\rightarrow$ `SIGSEGV` (Segmentation Fault).
            
              
            
        - Valid address $\rightarrow$ Major page fault; kernel initiates disk I/O to read page from swap/file.
            
              
            
    5. Thread is moved to **Blocked/Waiting** state; OS runs another process.
        
          
        
    6. Disk controller completes transfer, sends hardware interrupt.
        
          
        
    7. OS updates PTE with new PFN and sets `Present Bit = 1`.
        
          
        
    8. Process transitions to **Ready** queue; when scheduled, the faulting instruction restarts.
        
          
        
- **Copy-on-Write (CoW):**
    
      
    - `fork()` does not duplicate physical memory. It clones the page table entries and marks all shared pages as **Read-Only**.
        
          
        
    - When either parent or child attempts a write, the MMU triggers a page fault because of the read-only flag.
        
          
        
    - Kernel intercepts the fault, allocates a new physical frame, copies the 4 KB page data, updates the writing process's PTE to point to the new frame with **Write** enabled, and resumes execution.
        
          
        
- **Twisted Question:** _"Why does a 64-bit architecture use a 48-bit or 52-bit virtual address space instead of 64 bits?"_
    
      
    - **Answer:** A full 64-bit space would require 5–6 levels of page table hierarchies, causing excessive page-walk latency and massive page table memory overhead. 48 bits provides 256 TB per process, far exceeding present hardware memory limits.
        
          
        

**3. Concurrency, Locks & Memory Barriers**

  

- **Mutex vs. Spinlock vs. Binary Semaphore:**
    
      
    - **Mutex:** Sleep-lock with strict ownership. If locked, the caller yields the CPU and blocks in the kernel wait queue.
        
          
        
    - **Spinlock:** Busy-waiting loop utilizing atomic CPU instructions (e.g., `test_and_set`, `compare_and_swap`). Does not yield or context switch. **Never use spinlocks on a single-core machine** (it starves the thread holding the lock) or across code that can sleep/page-fault.
        
          
        
    - **Semaphore:** Integer counter used for signaling. No ownership; thread A can call `wait()` (decrement) and thread B can call `signal()` (increment).
        
          
        
- **Why Peterson's Algorithm Fails on Modern CPUs:**
    
      
    - Relies on sequential memory consistency. Modern out-of-order processors and compiler optimization pipelines reorder independent store and load instructions. Without **memory barriers/fences** (`mfence`, `acquire`/`release` semantics), writes to shared flags become visible out of order to other cores.
        
          
        
- **False Sharing (Cache-Line Contention):**
    
      
    - Two threads modifying independent variables that reside on the same 64-byte hardware cache line.
        
          
        
    - Cache coherency protocols (e.g., MESI) constantly invalidate the entire cache line across CPU cores, degrading multi-threaded throughput to slower than single-threaded execution. Fix: Cache-line padding (`alignas(64)`).
        
          
        
- **Twisted Question:** _"Can a deadlock occur with only one thread and one lock?"_
    
      
    - **Answer:** Yes, if a non-recursive (non-reentrant) mutex is locked twice sequentially by the same thread. The thread blocks waiting for itself to release the lock.
        
          
        

**4. Process Lifecycle & System Traps**

  

- **System Call Anatomy:**
    
      
    - User-space code cannot jump directly into kernel memory addresses (blocked by hardware CPU privilege rings: Ring 3 vs Ring 0).
        
          
        
    - A system call sets the syscall number in an architecture register (e.g., `RAX` on x86-64), loads arguments into defined registers (`RDI`, `RSI`, `RDX`), and executes `syscall` / `sysenter`.
        
          
        
    - CPU transitions to Ring 0, saves user stack pointer, swaps to the kernel stack, and jumps to the hardcoded entry point in the Interrupt Descriptor Table (IDT).
        
          
        
- **Zombie vs. Orphan:**
    
      
    - **Zombie:** Process called `exit()`, code/memory/file descriptors freed, but its Process Control Block (PCB) remains in the OS process table to retain exit code and execution metrics until the parent invokes `wait()` or `waitpid()`.
        
          
        
    - **Orphan:** Parent died without calling `wait()`. The kernel automatically reparents the orphan to `init` / `systemd` (PID 1) or a PR_SET_CHILD_SUBREAPER, which periodically invokes `wait()` to clean up.
        
          
        
- **Twisted Question:** _"How do you kill a Zombie process?"_
    
      
    - **Answer:** You cannot `kill -9` a zombie because it is already dead (it has no code or process image). You must either signal its parent to call `wait()`, or kill the parent process so the zombie is reparented to PID 1, which reaps it.
        
          
        

**5. I/O Multiplexing & File Descriptors**

  

- **`select` / `poll` vs. `epoll` (Linux) / `kqueue` (BSD):**
    
      
    - **`select` / `poll`:** $O(N)$ complexity. Passes the entire array/bitset of monitored file descriptors into the kernel on every call. The kernel iterates through every single FD, checks readiness, and returns. The application must iterate through all FDs again to find which fired.
        
          
        
    - **`epoll`:** $O(1)$ amortized. Registers FDs once using a red-black tree inside kernel space. When an I/O event occurs, the network card/socket interrupt pushes an entry onto a ready linked list. `epoll_wait()` only sleeps until the ready list is non-empty and copies back _only_ active descriptors.
        
          
        
- **Edge-Triggered (ET) vs. Level-Triggered (LT):**
    
      
    - **Level-Triggered:** `epoll_wait` keeps firing repeatedly as long as data remains in the buffer.
        
          
        
    - **Edge-Triggered:** `epoll_wait` fires only once when the state shifts from unready to ready (new data arrives). The application **must** read non-blocking sockets in an explicit loop until `EAGAIN` or `EWOULDBLOCK`, otherwise remaining bytes stall indefinitely.
        
          
        
- **Twisted Question:** _"What happens when two processes open the same file via `open()` concurrently versus through `fork()`?"_
    
      
    - **Separate `open()` calls:** Two distinct open file table entries in the kernel; each process has an independent file offset pointer. Writes from one do not advance the read offset of the other.
        
          
        
    - **Inherited via `fork()`:** Both processes share the **exact same underlying open file table entry**. They share the file offset pointer. If the child reads 50 bytes, the parent's read position shifts forward by 50 bytes.
        
          
        

**6. Quick Edge-Case Verification Table**

| **Concept**            | **The Common Assumption**           | **The Twisted Reality / Edge Case**                                                                                                                  |
| ---------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`fork()`**           | Copies process memory entirely.     | Copies 0 pages upfront; uses Copy-on-Write (CoW). Only page tables are cloned.                                                                       |
| **`malloc()`**         | Allocates physical RAM immediately. | Allocates virtual address space only (via `brk` or `mmap`). RAM is committed on first write via page fault.                                          |
| **Atomic Ops**         | Disable interrupts globally.        | Disables interrupts nowhere on multicore; locks internal hardware bus or coordinates via L1/L2 cache coherency lines.                                |
| **`O_DIRECT`**         | Bypasses the disk drive.            | Bypasses the OS page cache entirely; does raw I/O directly between user-space buffers and storage.                                                   |
| **Priority Inversion** | Higher priority always runs.        | Low-priority thread holding a resource blocks a high-priority thread while an unrelated medium thread starves both. Solved via Priority Inheritance. |
